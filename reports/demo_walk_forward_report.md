## 1. Что в проекте является методом валидации/оптимизации

Из `README.md`, `KEY_FINDINGS_AND_METHODS.md`, `backend/app/domain/resolution.py`, `backend/app/backtest/optimizer.py`:

- Стратегия: **TWAP Inertia & Barrier Lock** для 5-минутных UP/DOWN рынков Polymarket.
- Ключевые фильтры:
  - `deviation_twap_pct` от TWAP-open;
  - математический барьер `B = |dev_twap_pct| * (60 - STC) / STC`;
  - token alignment / book guard: цена покупаемого токена не ниже порога, не выше max-ask, защита от frozen 50/50;
  - ликвидность/глубина стакана.
- Валидация исходов:
  1. token polarization около close: winning token ≈ 1, losing token ≈ 0;
  2. Chainlink/local TWAP close-vs-open;
  3. при конфликте/неопределённости — Gamma API как ground truth для закрытого рынка.
- WFO-поиск — rolling train→test, ранжирование параметров по прибыли с штрафом за drawdown и бонусом за число сделок.

### Главная проблема качества: `twap` / `twap_open`

В данных есть очевидные сбои масштаба/символа в официальном TWAP-потоке, например:

- BTC `oracle_price≈76392`, но `twap≈338` или `twap≈23160`;
- ETH `oracle_price≈2402`, но `twap≈636`;
- SOL/XRP чаще имеют нормальный `twap`, но иногда испорчен `twap_open`, что даёт `deviation_twap_pct` десятки/сотни процентов.

Поэтому для WFO я применил sanity filter: строка с TWAP используется только если `twap` и `twap_open` находятся в пределах 2% от одновременно залогированных spot oracle / implied open. Это широкий порог для 60-секундного TWAP, но он отсекает именно патологические значения.

Вывод: **сырые логи нельзя использовать для оптимизации TWAP-параметров без фильтра качества**. После фильтра — можно, но результат остаётся exploratory из-за короткого периода и малого числа сделок.

## 4. WFO-конфигурация

Скрипт: `tools/demo_log_wfo.py`.

- Rolling folds: `train=144` интервала (~12ч), `test=48` интервалов (~4ч), step = 48.
- Начальный капитал fold/test: `$100`.
- Stake ratio: `20%`.
- Исполнение: ask + 0.01 slippage, cap 0.999.
- Fee: Polymarket crypto dynamic taker fee `0.07 * p * (1-p)` на акцию.
- Min order: 5 shares.
- Entry selection внутри интервала: max `barrier_pct`, затем max `|dev_twap_pct|`, затем более ранний timestamp.
- Grid:
  - STC windows: `10..35`, `2..30`, `2..7`, `2..12`, `2..15`, `2..60`;
  - `min_dev_pct`: `0.015`, `0.02`, `0.03`, `0.04`, `0.05`;
  - `min_barrier_pct`: `0.05`, `0.07`, `0.08`, `0.10`;
  - `min_token_ask`: `0.50`, `0.52`, `0.55`, `0.60`, `0.65`;
  - `max_token_ask`: `0.90`, `0.92`, `0.94`, `0.96`;
  - `full_book`: `false/true`.

## 6. Интерпретация по активам

### BTC

Результат неустойчивый: 5 побед подряд не компенсировали один поздний loss (`btc-updown-5m-1789647600`, entry≈0.63), потому что проигрыш бинарного токена уничтожает почти весь stake. При текущей выборке BTC **не подтверждён** для включения по этим параметрам.

### ETH

Единственный актив с положительным OOS в основном прогоне: +8.13% при 7 сделках. Но статистически это всё ещё очень малая выборка; один loss уже дал DD≈9.6%. ETH можно оставить в watchlist/демо, но не считать production-доказательством.

### SOL

Фильтры дают всего 1 OOS-сделку. Это **недостаточно для WFO-вывода**: формально плюс, но параметрическая оптимизация по SOL невалидна из-за редкости сигналов.

### XRP

Явно плохой OOS: -58.33%, WR 50%, DD 62%. XRP по этим логам и TWAP-фильтрам нужно отключить или требовать отдельный, значительно более строгий фильтр.

## 7. Финальный вывод о пригодности данных

**Да, данные пригодны для исследовательской walk-forward оптимизации после обязательной очистки**, потому что:

- есть ~46 часов непрерывных данных;
- по каждому активу 554 интервала;
- покрытие final-60 и entry-window почти полное;
- стаканы и token outcomes присутствуют почти всегда.

**Нет, данные пока недостаточны для production-решения**, потому что:

- период короткий: меньше двух суток;
- после TWAP sanity filter остаётся только 67–81% интервалов с пригодным TWAP;
- OOS-сделок очень мало: 1–8 на актив;
- сырые `twap` / `twap_open` содержат масштабные ошибки, способные создавать ложные `twap_barrier_locked`;
- конфликтные исходы сильно меняют картину, особенно BTC/ETH.

Практический вердикт:

- **ETH**: можно продолжать demo/walk-forward сбор, но без реальных денег до расширения выборки.
- **BTC**: не включать в live по текущему WFO; требуется больше Gamma-validated данных и устранение TWAP feed bugs.
- **SOL**: данных о сигналах недостаточно.
- **XRP**: отключить/не торговать в TWAP Inertia на текущей конфигурации.

## 8. Рекомендации

1. Добавить live sanity guard в `TWAPInertiaStrategy`: не использовать `cur_twap`/`twap_open`, если они отличаются от spot oracle / interval open больше допустимого порога.
2. Логировать в samples явный `twap_source` (`official` vs `reconstructed`), `start_price`, `up_token_id`, `down_token_id`, `market_closed`, `gamma_outcome` после закрытия.
3. Для WFO хранить локальный Gamma cache по всем `cross_disagree`, `twap_only`, `unresolved` slugs.
4. Минимальная production-выборка: хотя бы 7–14 дней и не менее 30–50 OOS-сделок на актив после всех фильтров.
5. Не считать neutral `cross_disagree` нулевым PnL в метриках стратегии: это маскирует реальные win/loss и искажает оптимизацию.
